# نازمارکت — فروش، مدیریت و ارسال یکپارچه

چهار رابط مستقل React/Vite به یک API و MySQL 8 متصل‌اند. هیچ فروشگاه، کالا، سفارش یا آمار نمایشی در مسیرهای عملیاتی seed نمی‌شود.

| بخش | مسیر | پورت توسعه |
| --- | --- | --- |
| API مشترک | `backend` | 4000 |
| فروشگاه مشتری | `frontend` | 5173 |
| پنل فروشنده | `seller-frontend` | 5174 |
| پنل سفیر | `courier-frontend` | 5175 |
| مدیریت اصلی | `admin-frontend` | 5176 |

## پیش‌نیاز و راه‌اندازی

Node.js 22.5+ و MySQL 8+ لازم‌اند. قبل از ارتقای محیط واقعی از **دیتابیس، تصاویر و کلید رمزگذاری** نسخه پشتیبان بگیرید.

```sql
CREATE DATABASE nazmarket CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

1. فایل `backend/.env.example` را به `backend/.env` کپی کنید.
2. مقادیر `MYSQL_*` را برای دیتابیس خود تنظیم کنید.
3. برای `SELLER_PII_KEY` یک کلید پایدار ۳۲ بایتی بسازید:

```sh
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

این کلید برای اطلاعات فروشنده و رمزگذاری مدارک سفیر استفاده می‌شود. آن را خارج از Git، همراه با پشتیبان امن نگهداری کنید. تغییر یا گم‌شدن کلید، مدارک قبلی را غیرقابل بازیابی می‌کند.

4. `ADMIN_USERNAME` و `ADMIN_PASSWORD_HASH` را تنظیم کنید.

**روش ساده در CMD، PowerShell و Linux/macOS:** داخل پوشهٔ `backend`، `node hash-admin-password.js` را اجرا کنید؛ پیام ورود رمز نمایش داده می‌شود. رمز جدید حداقل ۱۲ نویسه را وارد و فقط **Enter** بزنید. رمز نمایش داده نمی‌شود و نیازی به Ctrl+Z نیست. خط کامل `ADMIN_PASSWORD_HASH='scrypt$...'` خروجی را در `backend/.env` جایگزین کنید، `ADMIN_USERNAME=admin` را هم تنظیم و بک‌اند را ری‌استارت کنید. در پنل با رمز واردشده لاگین کنید، نه با هش. روش‌های pipe زیر همچنان فقط هش خام تولید می‌کنند.

 رمز پیش‌فرض یا مسیر ثبت‌نام عمومی مدیر وجود ندارد. رمز مدیر حداقل ۱۲ نویسه باشد؛ ابزار زیر رمز را از stdin دریافت می‌کند و فقط هش scrypt را چاپ می‌کند:

```sh
cd backend
npm ci
# Bash: رمز در history یا آرگومان پردازش قرار نمی‌گیرد
read -rs -p 'Admin password: ' ADMIN_PASSWORD; echo
printf '%s' "$ADMIN_PASSWORD" | node hash-admin-password.js
unset ADMIN_PASSWORD
```

PowerShell 7:

```powershell
Read-Host 'Admin password' -MaskInput | node hash-admin-password.js
```

خروجی کامل را در `.env` داخل کوتیشن تکی در `ADMIN_PASSWORD_HASH='scrypt$...'` قرار دهید. کلید و هش را در چت یا مخزن قرار ندهید.

5. API را از پوشهٔ `backend` اجرا کنید:

```sh
npm run dev
```

`npm run dev` فقط فایل‌های JavaScript مستقیم پوشهٔ backend و routes و فایل `.env` را با watcher غیر‌بازگشتی پایش می‌کند؛ پس از ذخیرهٔ کد، API قبلی متوقف و نسخهٔ تازه اجرا می‌شود. نوشتن تصاویر در uploads/private-uploads باعث ری‌استارت نمی‌شود. برای اولین ارتقا از اجرای قدیمی `node index.js`، یک بار ترمینال بک‌اند را با Ctrl+C متوقف و `npm run dev` را دوباره اجرا کنید. `npm start` برای اجرای بدون watcher در محیط واقعی باقی است.

migrationهای idempotent در شروع اجرا می‌شوند. بدون MySQL، API عمداً با خطا متوقف می‌شود؛ به دادهٔ ساختگی fallback نمی‌کند.

6. هر رابط را در ترمینال جدا اجرا کنید:

```sh
cd frontend # یا seller-frontend / courier-frontend / admin-frontend
npm ci
npm run dev
```

همهٔ رابط‌ها از `/api` و proxy به API استفاده می‌کنند. برای مقصد متفاوت، `API_PROXY_TARGET` را در محیط Vite تنظیم کنید. سرورهای توسعه به `0.0.0.0` bind می‌شوند و از میزبان preview پشتیبانی می‌کنند. در محیط واقعی فایل‌های `dist` را پشت HTTPS و reverse proxy هم‌مبدأ منتشر کنید؛ Vite سرور production نیست.

## بانک مرکزی و تصاویر

- مدیر محصول را با نام، توضیحات، دسته، واحد، قیمت پایه، وزن، سقف تخفیف و تصویر ثبت و ویرایش می‌کند.
- تصویر واقعی با Sharp decode می‌شود؛ EXIF حذف، جهت تصویر اصلاح و بدون crop با padding سفید به **JPEG مربع ۱۰۰۰×۱۰۰۰** تبدیل می‌شود. حداکثر آپلود هر فایل ۵ مگابایت است.
- نمایش تصویر در کارت، جزئیات، سبد، محصولات اخیر و پنل‌ها با نسبت ۱:۱ و `object-fit: contain` است؛ بسته‌بندی محصول بریده یا کشیده نمی‌شود.
- فروشگاه فقط لوگو دارد؛ عکس داخلی فروشگاه درخواست یا نمایش داده نمی‌شود.
- کالاهای واقعی قبلی بدون حذف به بانک منتقل می‌شوند؛ تصویر محلی معتبر آن‌ها به فایل مربع جدید تبدیل می‌شود. فایل اصلی حذف نمی‌شود. نبودن فایل رسانهٔ قدیمی در log گزارش می‌شود و تصویر ساختگی جایگزین نمی‌شود؛ پوشهٔ uploads محیط قبلی باید در استقرار جدید هم بازیابی شود.
- فروشنده فقط کالا را از بانک انتخاب می‌کند و قیمت، درصد تخفیف و موجودی مستقل خود را ویرایش می‌کند. تغییر نام، عکس، دسته، active یا ایجاد کالای دلخواه در سرور رد می‌شود. حذف کالا فقط به‌صورت غیرفعال‌سازی توسط مدیر است تا سوابق سفارش حفظ شود.
- ویرایش مرکزی نام/عکس/دسته/واحد، به عرضه‌های فروشندگان منتقل می‌شود؛ قیمت فروش مستقل فروشنده باقی می‌ماند. کاهش سقف مجاز، تخفیف‌های قبلی بیش از سقف را اصلاح می‌کند. سفارش‌های گذشته snapshot خود را حفظ می‌کنند.
- موجودی هر فروشنده **مستقل** است؛ در تراکنش با قفل عرضهٔ همان فروشنده کم می‌شود و لغو مجاز آن را برمی‌گرداند. مدیر مقدار موجودی تعیین نمی‌کند. انتخاب گروهی کالا از بانک با موجودی صفر آغاز می‌شود و فروشنده سپس قیمت و تعداد قابل فروش را وارد می‌کند.
- فروشگاه تازه تا تأیید مدیر در کاتالوگ عمومی فعال نمی‌شود.

## چرخهٔ پنج‌مرحله‌ای سفارش

| مقدار | وضعیت | ثبت‌کننده |
| --- | --- | --- |
| 1 | ثبت سفارش | مشتری |
| 2 | در حال آماده‌سازی | فروشندهٔ همان فروشگاه |
| 3 | آماده تحویل به سفیر | فروشندهٔ همان فروشگاه |
| 4 | تحویل به سفیر / در حال ارسال | سفیر تأییدشده هنگام دریافت |
| 5 | تکمیل سفارش | فقط همان سفیر واگذارشده |
| 0 | رد/لغو | مشتری فقط در وضعیت ۱؛ فروشنده در وضعیت ۱ یا ۲ با دلیل |

واگذاری و تغییر وضعیت اتمیک است؛ دو سفیر نمی‌توانند یک سفارش را دریافت کنند. فروشنده نمی‌تواند مراحل ۴ و ۵ را ثبت کند. همهٔ تغییرات همراه با نقش، شناسه و زمان در `order_events` ثبت می‌شوند و تاریخچهٔ کامل در پنل مدیریت خوانده می‌شود.

- **رد فروشگاه**: `POST /api/seller/orders/:id/reject` با `{reason, note}` فقط برای سفارشِ وضعیت ۱ یا ۲ کار می‌کند (پیش از تحویل به سفیر). در همان تراکنش `status=0` با `rejected_by='seller'` و `reject_reason` نوشته می‌شود، موجودی کالاها برمی‌گردد و `releasePromo` کد یک‌بارمصرف را به حساب مشتری بازمی‌گرداند. دلیل از فهرست پنج‌گانهٔ فروشگاه (`stock|closed|capacity|area|other`) ساخته می‌شود و توضیح اختیاری تا ۱۴۰ نویسه به آن می‌چسبد؛ متن نهایی همان چیزی است که مشتری می‌خواند.
- **آنچه مشتری می‌بیند سه گام است** (آماده‌سازی → تحویل به سفیر/ارسال فروشگاه → تقدیم به شما شده)؛ «ثبت سفارش» و «آماده تحویل» از دید او برداشته شده‌اند و وضعیت ۵ با عبارت «تقدیم به شما شده» خوانده می‌شود. شمارهٔ سفارش، دکمهٔ «خرید مجدد»، «پشتیبانی» و «مشاهده تاریخچه سفارش» از کارت حذف شده‌اند و سطر اول کارت یک جمله است: «سفارش در ساعت ۲۱:۳۲ ثبت شد · تحویل به خانه».
- پیام رد شدن در دو جا می‌آید: بنر بالای صفحهٔ اصلی (با دکمهٔ «انتخاب فروشگاه» و بستنی که در `localStorage` کلید `naz_reject_seen` ماندگار می‌شود) و بلوک قرمز همان کارت در «تاریخچه سفارش‌ها». بنر از همان فهرست `GET /api/orders` خوانده می‌شود، پس با باز کردن برنامه یا بازدید از صفحهٔ سفارش‌ها تازه می‌شود. سفارش‌های تکمیل‌شدهٔ نسخهٔ قبلی به وضعیت ۵ منتقل می‌شوند و سفارش‌های قبلاً دریافت‌شده به ۴؛ migration تکرار نمی‌شود.

به‌روزرسانی سفارش مشتری هر ۱۵ ثانیه در صفحهٔ سفارش‌ها، فروشنده و سفیر هر ۳۰ ثانیه، داشبورد مدیریت هر ۶۰ ثانیه است. دکمهٔ refresh هم وجود دارد.

## رابط مشتری: کارت‌ها، سبد و نویگیشن

- کارت کالا در یک نگاه: قیمت با `15px` (موبایل `13px`) پررنگ‌ترین سطر است و مبلغ تخفیف زیر آن به‌صورت «۹۰٬۰۰ تومان تخفیف» نوشته می‌شود؛ قیمت خط‌خوردهٔ قدیم دیگر در کارت نیست. ردیف‌ها فشرده‌ترند: `7` کارت در هر ردیف دسکتاپ، `4.5` در تبلت و `2.65` در موبایل؛ شبکهٔ فهرست هم تا `2xl:grid-cols-7` می‌رود.
- «دسته‌بندی‌ها» در خانه و «دسترسی سریع به دسته‌ها» در خریدِ راحت یک شبکهٔ واحد (`market-cat-grid`) با کاشی‌های هم‌اندازه‌اند؛ کاشیِ خالی نمایش داده نمی‌شود و ترتیب بر پایهٔ تعداد کالای موجود است (`categoryShelf`)؛ در موبایل یک ردیف افقی با snap است تا ردیفِ نیمه‌پر از بین برود.
- سبد خرید در دسکتاپ دیالوگ وسط‌چین است (`cart-sheet` با `md:w-[520px]` و انیمیشن `cart-pop-in`)، نه پنلی چسبانده به یک لبه؛ در موبایل همان برگهٔ تمام‌صفحه است. آیکون سبد در هدر هم‌رنگ بقیهٔ آیکون‌هاست (`bg-brand-soft` + `text-brand`).
- پیشنهادیِ داخل پاپ‌آپ کالا فقط در نسخهٔ موبایل می‌ماند (`product-modal-suggestions … md:hidden`) و در دسکتاپ نمایش داده نمی‌شود.
- تیترِ صفحه‌هایی که دکمهٔ بازگشتِ آن‌ها در دسکتاپ حذف می‌شود (`screen-heading no-desktop-heading`) کامل حذف است، تا عنوان بی‌دکمه روی صفحه نماند؛ `ScreenHeader` برای این کار prop یکی به نام `hideOnDesktop` دارد.
- نویگیشن موبایل کوچک‌تر شد: برند `18px` (قبلاً `25px`)، ارتفاع هدر `54px`، نوار جست‌وجو `42px` و برچسب‌های نوار پایین `7.5px`.
- فونت هر چهار اپ یکی است: Vazirmatn با همان استک `ui-sans-serif, system-ui` و پیش‌فرضِ Tahoma فقط به‌عنوان fallback. انتخاب‌گر تاریخ شمسی از `shared/persianDateField.css` در سراسر پنل‌ها همان فونت را به ارث می‌برد.

## پیشنهاد خرید اول

- فقط حساب واردشده و بدون هیچ سفارش قبلی واجد شرایط است.
- فقط **یک واحد از یک نوشیدنی انتخاب‌شده** نصف قیمت می‌شود؛ دو نوشیدنی و دو کیک، فقط یک تخفیف نصف قیمت یک نوشیدنی می‌گیرند.
- قیمت و دسته از دیتابیس خوانده می‌شود؛ مبلغ/discount ارسالی مرورگر قابل اعتماد نیست.
- قفل ردیف کاربر در تراکنش، بررسی سابقه و جدول `first_offer_redemptions` با کلید یکتای کاربر، مانع مصرف هم‌زمان یا دوباره می‌شوند.
- لغو سفارش، امکان استفادهٔ مجدد ایجاد نمی‌کند. نیمِ تومان در قیمت فرد به نفع مبلغ صحیح به پایین گرد می‌شود.
- کد تخفیف فروشگاه قابلیت جداگانهٔ موجود است و مبلغ آن جدا از پیشنهاد یک‌واحدی محاسبه می‌شود.

## کدهای تخفیف (فروشگاه و سراسری)

- دو خانوادهٔ کد وجود دارد: `seller_promos` (کد یک فروشگاه) و `platform_promos` (کد سراسری که فقط در پنل مدیریت ساخته می‌شود). مبلغ تخفیف در `orders.discount` (فروشگاه) و `orders.platform_discount` (نازمارکت) جدا ثبت می‌شود و کارمزد فروشنده از `subtotal − تخفیف فروشگاه` حساب می‌شود، پس یارانهٔ کد سراسری از جیب فروشنده نمی‌رود.
- هر کد، فروشگاه یا سراسری، **به ازای هر حساب یک‌بارمصرف** است: جدول `promo_redemptions` با کلید یکتای `(scope, promo_id, user_id)` جلوی مصرف دوباره را می‌گیرد و `max_uses` یک سقف اختیاری کلّی اضافه می‌کند (`0` = بدون سقف). `POST /api/promos/apply` فقط پیش‌محاسبه می‌کند و چیزی مصرف نمی‌کند؛ مصرف و آزادسازی (`releasePromo`) درون همان تراکنش ساخت/لغو سفارش انجام می‌شود تا دو تسویهٔ هم‌زمان یک ظرفیت را نسوزانند.
- کد سراسری می‌تواند برای **همهٔ مشتریان** (`audience='all'`) یا برای **مشتریان انتخابی** (`audience='users'` + جدول `platform_promo_users`) هدف بگیرد؛ `GET /api/promos` برای مشتری فقط کدهایی را برمی‌گرداند که واقعاً در حساب او کار می‌کنند.
- تاریخ شروع/پایان در پنل‌های فروشنده و مدیریت با **انتخاب‌گر تاریخ شمسی** (`shared/persianDate.ts` + `PersianDateField.tsx`) گرفته می‌شود و به همان `YYYY-MM-DD` میلادی به سرور می‌رود. یک روزِ انتخاب‌شده به کلّ آن روز ترجمه می‌شود (`promoDateBound`)، پس «پایان: امروز» تا آخرین دقیقهٔ همان روز معتبر می‌ماند و تاریخ گذشته رد می‌شود. برچسب تاریخ‌ها در فهرست‌ها با `formatJalaliDay` خوانده می‌شود تا ساعتِ bound، روز را یک روز جلو نبرد.
- قفسهٔ «کدهای تخفیف من» در اپ مشتری از `GET /api/promos` خوانده می‌شود (نه از کاتالوگ عمومی): کدهای سراسری با برچسب «سراسری · نازمارکت»، کدهای فروشگاه با نام فروشگاه، و کدی که همان حساب مصرف کرده با برچسب «مصرف شده» و بدون دکمهٔ کپی در انتهای فهرست می‌آید. ظرفیت باقی‌مانده، حداقل سبد و سقف تخفیف هم روی کارت نمایش داده می‌شود؛ مهمان (بدون نشست) فقط کدهای عمومی فروشگاه را می‌بیند.
- در کارت «کد تخفیف» مرحلهٔ تسویه هم همان خانواده اعلام می‌شود (برچسب «سراسری · نازمارکت» یا «ویژهٔ {فروشگاه}») و مبلغ کنار کد، `codeDiscount` است — یعنی فقط ارزش همان کد؛ مبلغ «تخفیف» در جمع‌وبند کل، که پیشنهاد خرید اول را هم جمع می‌کند، از آن جدا نوشته می‌شود. برای کد سراسری یک خط توضیح می‌آید که این سهم را نازمارکت می‌دهد و کارمزد فروشگاه کم نمی‌شود (تقسیم واقعی در سرور ثبت می‌شود: `orders.discount` کل، `orders.platform_discount` سهم پلتفرم).
- فیش سفارش در اپ مشتری از ردیفی که سرور نوشته ساخته می‌شود (`Receipt` در `pages/CartFlow.tsx`): جمع کالاها، تخفیف (با کد استفاده‌شده)، هزینه ارسال و قابل پرداخت — و وقتی ستون‌های تفکیک پر باشند، سهم نازمارکت / فروشگاه / پیشنهاد خرید اول هم نوشته می‌شود. اگر مجموع سهم‌ها با `orders.discount` هم‌خوان نباشد (سفارش‌های قدیمی‌تر از این ستون‌ها) فقط کل تخفیف نمایش داده می‌شود، نه تقسیمی که سرور ثبت نکرده. در کارت سفارش در «سفارش‌ها» هم سطر تخفیف و سهم نازمارکت می‌آید.
- در پنل مدیریت، بخش **کدهای تخفیف** ساخت/ویرایش/غیرفعال‌سازی و گزارش مصرف هر کد را می‌دهد و بخش **کاربران** فهرست کامل مشتریان را با نام، موبایل، تعداد سفارش، مبلغ خرید تکمیل‌شده، آخرین سفارش، کدهای مصرفی و تاریخ عضویت (شمسی) نشان می‌دهد؛ جست‌وجو، فیلتر «با سفارش/بدون سفارش» و «مصرف کد»، مرتب‌سازی (از جمله بر پایهٔ بیشترین کد مصرفی) و خروجی CSV همان پرسش سرور را ورق می‌زند. کد مصرف‌شده قابل حذف نیست و فقط غیرفعال می‌شود تا سابقهٔ سفارش‌ها حفظ شود. دکمهٔ «مشتریان» زیر هر کد سراسری فهرست مصرف‌کنندگان را از `GET /api/admin/operations/promos/:id/redemptions` باز می‌کند (نام، موبایل، شمارهٔ سفارش، مبلغ و تاریخ‌وساعت شمسی؛ ۲۰۰ ردیف اخیر با شمارش کل). برای کد فروشگاه این فهرست در پنل فروشنده نیامده — فروشنده فقط تعداد مصرف و سقف را می‌بیند، چون شمارهٔ مشتری متعلق به حساب او نیست.

## احراز هویت سفیر و امنیت مدارک

سفیر پس از ثبت‌نام می‌تواند وارد شود، اما قبل از تأیید مدارک هیچ دسترسی به سفارش‌ها ندارد. نام و موبایل در ثبت‌نام گرفته می‌شود؛ فرم احراز شامل شماره پلاک، مدل و رنگ وسیله، عکس موتور، عکس پلاک، کارت ملی و گواهینامه موتور است.

وضعیت‌ها: ارسال‌نشده، در انتظار بررسی، تأییدشده، ردشده و نیازمند اصلاح مدارک. مدیر مدارک را می‌بیند و نتیجه را با دلیل ثبت می‌کند. رد/اصلاح اجازهٔ ارسال مجدد می‌دهد؛ درخواست pending یا approved قابل overwrite توسط سفیر نیست.

- مدارک decode و به JPEG امن تبدیل و با **AES-256-GCM** در `backend/private-uploads` رمزگذاری می‌شوند؛ این مسیر هیچ static mount عمومی ندارد.
- دسترسی تصویر تنها با نشست معتبر مدیر (انقضای ۸ ساعت) و پاسخ `Cache-Control: no-store` ممکن است.
- فایل‌ها permission محدود دارند و همراه `.env` و uploads از Git خارج‌اند. در محیط واقعی TLS، دسترسی محدود سیستم‌عامل و پشتیبان رمزگذاری‌شده ضروری است.
- حتی تغییر دستی `active=1` بدون `verification_status='approved'` امکان دریافت سفارش نمی‌دهد.
- ورود مدیر، فروشنده و سفیر throttle دارد و حوزهٔ نشست‌هایشان جداست.

## داشبورد مدیریت

آمار کل/فعال/غیرفعال کاربران و فروشندگان، وضعیت احراز سفیرها، تمام وضعیت‌های سفارش، فروش کل/روزانه/ماهانه، مجموع تخفیف و گزارش عملکرد فروشنده و سفیر مستقیماً از دیتابیس محاسبه می‌شود. کاربران و سفارش‌ها جست‌وجوی سمت سرور و صفحه‌بندی دارند؛ محصولات و مدارک و فروشگاه‌ها فیلتر/جست‌وجو و کنترل وضعیت دارند.

تعریف‌ها در رابط مشخص‌اند:

- کاربر فعال: حداقل یک ورود در ۳۰ روز اخیر؛ «غیرفعال» در این آمار به معنی مسدود بودن حساب نیست.
- فروشنده فعال: حساب و فروشگاه هر دو فعال.
- فروش: مجموع مبلغ نهایی سفارش‌های تکمیل‌شده؛ **به معنی تأیید تراکنش بانکی نیست**.
- گزارش روزانه و ماهانه بر مبنای UTC و ماه میلادیِ `created_at` سفارش است.
- تخفیف کل مربوط به سفارش‌های غیرلغوشده است.

نشست مدیریت یک توکن ۸ ساعته در `admin_sessions` است و با هر درخواست معتبر تمدیم می‌شود؛ بنابراین پنلی که روشن مانده در میانهٔ کار ناگهان 401 نمی‌گیرد، اما پس از ۸ ساعت بی‌کاری با پیام «نشست مدیریت تمام شده است؛ دوباره وارد شوید.» به فرم ورود برمی‌گردد. توکن در `sessionStorage` است و با بستن تب پاک می‌شود. کلاینت هیچ درخواست نیازمند احراز هویت را بدون توکن نمی‌فرستد (در غیر این صورت مرورگر خطای 401 را در کنسول ثبت می‌کند حتی وقتی پنل سالم است) و چند پاسخ 401 هم‌زمان فقط یک بار به صفحهٔ ورود می‌برد. کارت‌های آمار و جدول‌ها تا رسیدن نخستین پاسخ جای خود را با اسکلتون نگه می‌دارند، نه با عدد صفر. فاصلهٔ ۶۰ ثانیه‌ای تازه‌سازی و ۳۰ ثانیه‌ای جدول سفارش بدون تغییر عرض دکمهٔ «به‌روزرسانی» انجام می‌شود.

## بررسی و تست

```sh
cd backend
npm test
# بررسی syntax
node --check app.js

cd ../frontend
npm run typecheck
npm run build
# در seller-frontend، courier-frontend و admin-frontend هم typecheck و build اجرا شود.
```

تست‌های پیش‌فرض قواعد قیمت، یک‌واحد بودن تخفیف، محدودیت دسته، استفاده مجدد، ماتریس مجوز مراحل، تصویر مربع و رمزگذاری مدارک را بررسی می‌کنند. تست‌های HTTP دسترسی با persistence stub اجرا می‌شوند؛ با تست دیتابیس واقعی یکسان نیستند.

### تست سرتاسری با MySQL واقعی

فقط روی دیتابیس آزمایشی **خالی** با نام منتهی به `_test` اجرا شود. این تست رکورد آزمایشی ایجاد می‌کند و برای دیتابیس واقعی نیست:

```sh
# ابتدا CREATE DATABASE nazmarket_test و تنظیم MYSQL_* برای همین دیتابیس
RUN_MYSQL_TESTS=1 MYSQL_DATABASE=nazmarket_test npm run test:integration
```

در PowerShell متغیرها را با `$env:RUN_MYSQL_TESTS='1'` و `$env:MYSQL_DATABASE='nazmarket_test'` تنظیم کنید. تست شامل migration دوباره، ثبت‌نام فروشنده، تأیید فروشگاه، بانک کالا، محدودیت فروشنده، سفارش هم‌زمان خرید اول، موجودی، اصلاح/رد/تأیید مدارک، رقابت دو سفیر، تحویل نهایی، تاریخچه و آمار است. فایل `.github/workflows/verify.yml` همین سناریو را روی سرویس MySQL 8 در CI و Build هر چهار رابط اجرا می‌کند. بدون متغیر فعال‌سازی، تست MySQL **skip** می‌شود، نه موفقیت ظاهری.

## حدود استقرار

درگاه بانکی، SMS و سرویس استعلام رسمی هویت متصل نیستند؛ احراز هویت، بررسی انسانی مدارک است. پرداخت فعلاً در محل و `unpaid` ثبت می‌شود و تسویهٔ آنلاین فعال نیست. استقرار production نیازمند MySQL معتبر، متغیرهای مدیر و کلید امنیتی، رسانه‌های پایدار، HTTPS و بکاپ است. هیچ اطلاعات واقعی یا کلید امنیتی را برای تست در مخزن قرار ندهید.

## گردش کار و حسابداری جدید

- صفحهٔ اول محصولات قابل فروش را مستقیماً نشان می‌دهد. سفارش‌های فعال جدا از تاریخچه در تنظیمات هستند.
- سفیر بعد از ورود ساده، احراز مرحله‌ای را از تنظیمات انجام می‌دهد (۱ تا ۴ عکس موتور به‌همراه عکس پلاک و مدارک). سفیر تأییدشده با فعال کردن وضعیت کاری و موقعیت مرورگر، سفارش‌های تا شعاع ۱۵ کیلومتر را نزدیک‌ترین‌اول می‌بیند؛ موقعیت باید حداکثر ۱۵ دقیقه قدمت داشته باشد.
- کرایه عادی ۵۰–۸۰ هزار تومان و باران/برف حداکثر ۱۰۰ هزار تومان است. مسافت تخمینی خط مستقیم ×۱٫۳، زمان تخمینی و وزن در محاسبه اثر دارند؛ مسیریابی زنده نیست. شرایط جوی را مدیر تعیین می‌کند، نه سرویس آب‌وهوا.
- مبلغ کرایه فقط یک‌بار هنگام تحویل به دفتر کیف پول سفیر ثبت می‌شود. برداشت‌های در انتظار و پرداخت‌شده موجودی قابل برداشت را رزرو می‌کنند؛ رد درخواست رزرو را آزاد می‌کند. پرداخت بانکی خودکار نیست؛ مدیر پس از انتقال واقعی، مرجع پرداخت را ثبت می‌کند.
- سود عملیاتی ثبت‌شده = کمیسیون + کرایهٔ سفارش‌های تکمیل‌شده − یارانهٔ پیشنهاد اول − اعتبارهای دفتر سفیر − هزینه‌های عملیاتی ثبت‌شده. این عدد سود حسابرسی‌شده پس از مالیات یا هزینه‌های ثبت‌نشده نیست؛ سفارش‌های قدیمی بدون snapshot مالی/دفتر سفیر، نیازمند تطبیق حسابداری هستند. کمیسیون اولیه صفر است و مدیر می‌تواند آن را بین صفر تا ۳۰ درصد تنظیم کند.
- نقشه‌ها پس از تغییر اندازه بازتنظیم می‌شوند و در صورت خطای کاشی، سرویس جایگزین و پیام خطا دارند. دسترسی شبکه به سرویس کاشی لازم است؛ ورود دستی مختصات فروشگاه هم فراهم است.

### فونت مشترک و حالت بارگذاری در چهار رابط

وزیرمتن تنها فونت تمام پنل‌هاست و از همین میزبان سرو می‌شود: اپ مشتری فایل‌های `frontend/public/fonts` را با `unicode-range` عربی و لاتین بارگذاری می‌کند و سه پنل دیگر از بستهٔ `@fontsource-variable/vazirmatn` استفاده می‌کنند؛ هیچ `@import` یا لینک Google Fonts باقی نمانده، چون فونت CDN دیر می‌رسد (یا اصلاً نمی‌رسد) و هنگام رسیدن، صفحه را جابه‌جا می‌کند. `font-family` مشترک در `--font-sans` اپ مشتری و `:root` بقیهٔ پنل‌ها تعریف شده و `font-synthesis: none` وزن‌های جعلی را حذف می‌کند؛ چون فونت متغیر است، وزن‌های ۶۵۰/۷۵۰ واقعی رندر می‌شوند. فرم‌ها، دکمه‌ها، نوارها و برچسب وضعیت‌ها همگی `font-family: inherit` دارند تا هیچ المانی به فونت پیش‌فرض مرورگر برنگردد.

حالت بارگذاری استاندارد یکی است: به‌جای spinner تنها، جای هر بلوک با اسکلتون هم‌اندازهٔ محتوای نهایی پر می‌شود (کارت محصول و قفسه در اپ مشتری، کارت‌ها/عدد/جدول در پنل مدیریت، نقشه و فهرست پیشنهادها و رقم‌های هفته در پنل سفیر)، انیمیشن با `prefers-reduced-motion` خاموش می‌شود و عرض/ارتفاع المان‌ها در حالت لودینگ ثابت می‌ماند تا چیدمان نشکند.

### عیب‌یابی پنل سفیر

پیام React DevTools صرفاً پیشنهاد ابزار توسعه است. پاسخ 401 ورود یعنی اطلاعات ورود پذیرفته نشده؛ 500 خطای داخلی API است. در خطاهای داخلی، شناسهٔ پیگیری پاسخ را با خروجی `[api]` همان شناسه در ترمینال بک‌اند تطبیق دهید. لاگ تشخیصی شامل کد خطا و محل کد است و متن خطای دیتابیس/SQL، بدنهٔ درخواست، رمز و توکن را چاپ نمی‌کند. `ERR_CONNECTION_RESET` یعنی اتصال قطع شده و به‌تنهایی نشان‌دهندهٔ رمز نادرست نیست. برای تفکیک خطای proxy، در دستگاه اجرای سرور `http://localhost:4000/api/health` را بررسی کنید. کلید `SELLER_PII_KEY` باید ۶۴ نویسهٔ hex باشد؛ کلید فعال را تغییر ندهید، چون مدارک قبلی با آن رمز شده‌اند.

### پنل سفیر — طراحی واکنش‌گرا

داشبورد سفیر با سایدبار دسکتاپ و ناوبری پایین موبایل، فونت محلی وزیرمتن، نقشهٔ Leaflet، پیشنهادهای قبول/رد، کیف پول، گزارش هفت‌روزه و پشتیبانی طراحی شده است. گزارش `/api/courier/summary` از دفتر درآمد و تحویل‌های واقعی همان سفیر محاسبه می‌شود (روز و هفته بر مبنای UTC)؛ امتیاز، نرخ موفقیت یا آمار فرضی ندارد. تصویر تزئینی موتور تولیدشده با هوش مصنوعی است و هیچ شخص واقعی یا مدرک هویتی را نشان نمی‌دهد.

رد پیشنهاد در `courier_declined_orders` فقط برای همان سفیر ذخیره می‌شود؛ سفارش برای سفیرهای دیگر باقی می‌ماند. قبول پیشنهاد از دریافت بسته جداست: پذیرش → رسیدن به فروشگاه → دریافت بسته → تحویل با کد مشتری. پنج مرحلهٔ اصلی سفارش مشتری حفظ شده‌اند و ریزمراحل سفیر جداگانه ثبت می‌شوند. نقشهٔ خیابان‌ها و نقاط ثبت‌شده نمایش داده می‌شود، اما مسیر جاده‌ای یا زمان رسیدن زنده تولید نمی‌شود؛ مختصات مقصد مشتری فقط پس از دریافت سفارش به سفیر آن سفارش داده می‌شود. کاشی‌ها به دسترسی شبکه به CARTO یا OpenStreetMap نیاز دارند؛ خطای کاشی مانع استفاده از کارت سفارش نیست.

جعبهٔ نقشه ارتفاع ثابت ۳۲۰ پیکسلی دارد و تا پیش از آماده شدن نقشه یا نخستین پاسخ `/api/courier/orders` همان جایگاه را یک اسکلتون هم‌اندازه نگه می‌دارد (با پیام «در حال دریافت نقشه…» و سه کارت پیشنهاد در ستون فهرست)؛ به همین دلیل آمدن نقشه، هشدارها یا آمار هفته هیچ بلوکی را جابه‌جا نمی‌کند. لایهٔ اعلان‌ها `z-index: 1050` دارد — بالاتر از نقشهٔ Leaflet و از نوار ثابت پایین — پس کلیک روی اعلان هیچ‌وقت زیر نقشه یا عکس ثبت نمی‌شود. برچسب آیتم‌های نوار پایین موبایل ۷.۵ پیکسل است (هم‌اندازهٔ نوار پایین اپ مشتری) و `min-height: 48px` سطح لمسی را حفظ می‌کند.


مشخصات، قرارداد API و وضعیت پوشش سند محصول سفیر در [`docs/courier-product.md`](docs/courier-product.md) ثبت شده است. نسخهٔ جاری وب واکنش‌گراست؛ اپلیکیشن بومی Android/iOS، SMS و Push موبایل تحویل داده نشده‌اند.


### تشخیص بک‌اند قدیمی در عملیات ارسال فروشگاه

پاسخ `/api/health` نسخهٔ جاری باید `apiRevision: "seller-dispatch-v2"` و قابلیت‌های `sellerDispatch` و `sellerSelfDelivery` را با مقدار true داشته باشد. پنل فروشنده این پاسخ را از همان proxy عملیات سفارش بررسی می‌کند؛ اگر قدیمی باشد، دکمه‌های عملیات جدید غیرفعال و راهنمای راه‌اندازی نمایش داده می‌شود. ری‌استارت Vite به‌تنهایی پردازش قدیمی بک‌اند را عوض نمی‌کند. ابتدا بک‌اند قدیمی را متوقف و در پوشهٔ backend به‌روز `npm run dev` اجرا کنید. خط `[seller] API proxy:` در ترمینال Vite مقصد واقعی پراکسی را نشان می‌دهد. `API_PROXY_TARGET` هم از محیط پردازش و هم از فایل `.env` پنل فروشنده خوانده می‌شود؛ تغییر آن نیازمند ری‌استارت Vite است.

مسیریابی سفیر فقط مقصد را به Google Maps، نشان یا بلد می‌سپارد. در نشان، در صورت وجود مختصات سفیر، لینک مسیر با وسیلهٔ موتور ساخته می‌شود؛ در بلد مقصد باز می‌شود تا هدایت مسیر در همان برنامه آغاز شود. نصب و association لینک‌ها در گوشی، تعیین می‌کند اپ بومی یا وب سرویس باز شود؛ هیچ مسیر یا هدایت ساختگی در پنل تولید نمی‌شود.

### قفسه‌های صفحهٔ اصلی و خرید راحت
- صفحهٔ اصلی موبایل لوگو و جست‌وجوی ساده، ردیف افقی مستقل برای هر دستهٔ موجود، کارت محصول با تصویر مربعی، علاقه‌مندی و افزودن تکی دارد. کالا/برند یا کمپین نمایشی ساخته نمی‌شود.
- پیشنهاد خرید اول فقط برای کاربر واجد شرایط نمایش داده می‌شود: یک واحد از یک نوشیدنی با ۵۰٪ تخفیف. انتخاب مجدد همان کارت تعداد را زیاد نمی‌کند؛ عوض‌کردن انتخاب فقط کالای مشمول تخفیف را عوض می‌کند. تعداد اضافه در سبد با قیمت عادی فروشگاه محاسبه می‌شود. محدودیت خرید اول و یک واحد تخفیف سمت سرور و تحت قفل حساب کاربر اجرا می‌شود؛ سابقهٔ سفارش لغوشده نیز خرید اول را بازنمی‌گرداند.
- «خرید راحت» حداکثر ۸ کالای یکتای خریدهای تکمیل‌شدهٔ همان مشتری را با اولویت خرید جدیدتر و قیمت/موجودی کاتالوگ فعلی نشان می‌دهد. کالاهای حذف‌شده، غیرفعال، ناموجود یا متعلق به فروشگاه دیگر کنار گذاشته می‌شوند. سفارش‌ها و کاتالوگ در این صفحه تازه‌سازی می‌شوند؛ برچسب عمومی frequent مبنای شخصی‌سازی نیست. بدون سابقه، پیام صادقانهٔ خالی نمایش داده می‌شود.
- تست‌های منطق پیشنهاد شخصی در frontend با `npm test` اجرا می‌شوند و در CI رابط‌ها نیز اجرا می‌شوند.

قفسهٔ «تخفیف‌های شگفت‌انگیز» بعد از بخش خرید اول از کالاهای موجودی ساخته می‌شود که اختلاف قیمت واقعی فروشگاه با oldPrice آن‌ها **بیشتر از ۵٪** است؛ تخفیف دقیقاً ۵٪ وارد این بخش نمی‌شود و تخفیف تازه‌ای روی قیمت اعمال نمی‌شود. قفسهٔ پایین‌تر «بزن روشن شی» فقط نوشیدنی‌های موجود غیرآب را از ارزان به گران نمایش می‌دهد. نام‌های آب معدنی/آشامیدنی/گازدار و شکل‌های رایج نام آب حذف می‌شوند؛ «آبمیوه» و «آب میوه» حذف نمی‌شوند. چون نوع نوشیدنی مستقل در کاتالوگ وجود ندارد، تشخیص آب بر اساس نام کالا در دستهٔ نوشیدنی است.

در خرید راحت، دسته‌ها اولین بخش و کالاهای خرید قبلی زیر آن‌ها هستند؛ متن معرفی اضافه حذف شده است. عنوان و زیرعنوان بالای سفارش‌های فعال هم حذف شده‌اند. صفحات دسته (مانند نوشیدنی) جست‌وجوی محلی دارند. در موبایل، دکمهٔ برگشت آیکونی روی صفحات داخلی و جزئیات محصول نمایش داده می‌شود و ناوبری مرورگر/سیستم نیز حفظ است. پیشنهادهای داخل جزئیات محصول در ردیف افقی با کارت‌های ۱۸۴ پیکسلی و نام/قیمت خوانا ارائه می‌شوند. فوتر در موبایل پنهان است و در نمایشگر بزرگ چیدمان سه‌بخشی دارد: معرفی نازمارکت، پیوندهای واقعی قوانین/حریم خصوصی/پشتیبانی و محدودهٔ ارسال؛ نسخه و اطلاعات حق‌نشر در بخش لینک‌ها/معرفی می‌آیند. در صفحهٔ اصلی موبایل، با غیرخالی شدن سبد آیکون کوچک سبد در چپ سربرگ ظاهر می‌شود و آواتار حساب سمت راست می‌ماند؛ اندازهٔ نوشته‌های ناوبری دسکتاپ نیز کاهش یافته است. جزئیات سبد خرید لوگوی فروشگاه را هم از کاتالوگ واقعی نشان می‌دهد. قفسهٔ آبی «بزن روشن شی» برچسب تکراری ندارد و با روبان هدیه و شعار کوتاه تزئین شده است؛ رنگ‌آمیزی قفسه و نشان تخفیف خرید اول نیز با طیف‌های پررنگ‌تر و بافت نواری اجرا شده‌اند.

تصویر فروشگاه از `logo_url` و در نبود آن از `photo_url` دریافت می‌شود. نگاشت API اکنون هر دو را ارسال می‌کند و فهرست فروشگاه‌ها دیگر فقط فروشگاه‌های دارای لوگو را برنمی‌گرداند؛ اگر نشانی تصویر خراب باشد، حرف نخست نام فروشگاه جایگزین می‌شود. همین لوگو در سبد و مرحلهٔ تکمیل خرید هم می‌آید. هنگام بارگذاری اولیهٔ برنامه و تصاویر، اسکلت متحرک نمایش داده می‌شود؛ برای تصویر خراب fallback واقعی حفظ می‌شود. صفحهٔ خرید راحت از پس‌زمینهٔ سفید تمام‌عرض استفاده می‌کند. صفحهٔ حساب یک کارت گرد و یکپارچه دارد و فضای پایین آن برای ناوبری موبایل رزرو شده است. وضعیت انتخاب‌شدن آیتم‌های هدر نیز فقط به صفحهٔ جاری تعلق دارد.
