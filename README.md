# نازمارکت — فروش، مدیریت و ارسال یکپارچه

چهار رابط مستقل React/Vite به یک API و MySQL 8 متصل‌اند. هیچ فروشگاه، کالا، سفارش یا آمار نمایشی در مسیرهای عملیاتی seed نمی‌شود.

| بخش | مسیر | پورت توسعه |
| --- | --- | --- |
| API مشترک | `backend` | 4000 |
| فروشگاه مشتری | `frontend` | 5173 |
| پنل فروشنده | `seller-frontend` | 5174 |
| پنل پیک | `courier-frontend` | 5175 |
| مدیریت اصلی | `admin-frontend` | 5176 |

## پیش‌نیاز و راه‌اندازی

Node.js 22.5+ و MySQL 8+ لازم‌اند. قبل از ارتقای محیط واقعی از **دیتابیس، تصاویر و کلید رمزگذاری** نسخه پشتیبان بگیرید.

```sql
CREATE DATABASE nazmarket CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

1. فایل `backend/.env.example` را به `backend/.env` کپی کنید.
2. مقادیر `MYSQL_*` را برای دیتابیس خود تنظیم کنید.
3. برای `SELLER_PII_KEY` یک کلید پایدار ۳۲ بایتی بسازید:

```sh
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

این کلید برای اطلاعات فروشنده و رمزگذاری مدارک پیک استفاده می‌شود. آن را خارج از Git، همراه با پشتیبان امن نگهداری کنید. تغییر یا گم‌شدن کلید، مدارک قبلی را غیرقابل بازیابی می‌کند.

4. `ADMIN_USERNAME` و `ADMIN_PASSWORD_HASH` را تنظیم کنید. رمز پیش‌فرض یا مسیر ثبت‌نام عمومی مدیر وجود ندارد. رمز مدیر حداقل ۱۲ نویسه باشد؛ ابزار زیر رمز را از stdin دریافت می‌کند و فقط هش scrypt را چاپ می‌کند:

```sh
cd backend
npm ci
# Bash: رمز در history یا آرگومان پردازش قرار نمی‌گیرد
read -rs -p 'Admin password: ' ADMIN_PASSWORD; echo
printf '%s' "$ADMIN_PASSWORD" | node hash-admin-password.js
unset ADMIN_PASSWORD
```

PowerShell 7:

```powershell
Read-Host 'Admin password' -MaskInput | node hash-admin-password.js
```

خروجی کامل را در `.env` داخل کوتیشن تکی در `ADMIN_PASSWORD_HASH='scrypt$...'` قرار دهید. کلید و هش را در چت یا مخزن قرار ندهید.

5. API را از پوشهٔ `backend` اجرا کنید:

```sh
npm run dev
```

migrationهای idempotent در شروع اجرا می‌شوند. بدون MySQL، API عمداً با خطا متوقف می‌شود؛ به دادهٔ ساختگی fallback نمی‌کند.

6. هر رابط را در ترمینال جدا اجرا کنید:

```sh
cd frontend # یا seller-frontend / courier-frontend / admin-frontend
npm ci
npm run dev
```

همهٔ رابط‌ها از `/api` و proxy به API استفاده می‌کنند. برای مقصد متفاوت، `API_PROXY_TARGET` را در محیط Vite تنظیم کنید. سرورهای توسعه به `0.0.0.0` bind می‌شوند و از میزبان preview پشتیبانی می‌کنند. در محیط واقعی فایل‌های `dist` را پشت HTTPS و reverse proxy هم‌مبدأ منتشر کنید؛ Vite سرور production نیست.

## بانک مرکزی و تصاویر

- مدیر محصول را با نام، توضیحات، دسته، واحد، قیمت پایه، موجودی مرکزی، سقف تخفیف و تصویر ثبت و ویرایش می‌کند.
- تصویر واقعی با Sharp decode می‌شود؛ EXIF حذف، جهت تصویر اصلاح و بدون crop با padding سفید به **JPEG مربع ۱۰۰۰×۱۰۰۰** تبدیل می‌شود. حداکثر آپلود هر فایل ۵ مگابایت است.
- نمایش تصویر در کارت، جزئیات، سبد، محصولات اخیر و پنل‌ها با نسبت ۱:۱ و `object-fit: contain` است؛ بسته‌بندی محصول بریده یا کشیده نمی‌شود.
- فروشگاه فقط لوگو دارد؛ عکس داخلی فروشگاه درخواست یا نمایش داده نمی‌شود.
- کالاهای واقعی قبلی بدون حذف به بانک منتقل می‌شوند؛ تصویر محلی معتبر آن‌ها به فایل مربع جدید تبدیل می‌شود. فایل اصلی حذف نمی‌شود. نبودن فایل رسانهٔ قدیمی در log گزارش می‌شود و تصویر ساختگی جایگزین نمی‌شود؛ پوشهٔ uploads محیط قبلی باید در استقرار جدید هم بازیابی شود.
- فروشنده فقط کالا را از بانک انتخاب می‌کند و قیمت و درصد تخفیف آن را ویرایش می‌کند. تغییر نام، عکس، دسته، موجودی، active یا ایجاد کالای دلخواه در سرور رد می‌شود. حذف کالا فقط به‌صورت غیرفعال‌سازی توسط مدیر است تا سوابق سفارش حفظ شود.
- ویرایش مرکزی نام/عکس/دسته/واحد و موجودی، به عرضه‌های فروشندگان منتقل می‌شود؛ قیمت فروش مستقل فروشنده باقی می‌ماند. کاهش سقف مجاز، تخفیف‌های قبلی بیش از سقف را اصلاح می‌کند. سفارش‌های گذشته snapshot خود را حفظ می‌کنند.
- موجودی در این مدل **مشترک و مرکزی** است؛ در تراکنش با قفل کالا کم می‌شود و به عرضه‌های مرتبط همگام می‌شود. لغو مجاز موجودی را برمی‌گرداند. تغییر موجودی فقط با مدیر است.
- فروشگاه تازه تا تأیید مدیر در کاتالوگ عمومی فعال نمی‌شود.

## چرخهٔ پنج‌مرحله‌ای سفارش

| مقدار | وضعیت | ثبت‌کننده |
| --- | --- | --- |
| 1 | ثبت سفارش | مشتری |
| 2 | در حال آماده‌سازی | فروشندهٔ همان فروشگاه |
| 3 | آماده تحویل به پیک | فروشندهٔ همان فروشگاه |
| 4 | تحویل به پیک موتوری / در حال ارسال | پیک تأییدشده هنگام دریافت |
| 5 | تکمیل سفارش | فقط همان پیک واگذارشده |
| 0 | لغوشده | مشتری، فقط پیش از شروع آماده‌سازی |

واگذاری و تغییر وضعیت اتمیک است؛ دو پیک نمی‌توانند یک سفارش را دریافت کنند. فروشنده نمی‌تواند مراحل ۴ و ۵ را ثبت کند. همهٔ تغییرات همراه با نقش، شناسه و زمان در `order_events` ثبت می‌شوند؛ تاریخچه در مدیریت و سفارش‌های مشتری قابل مشاهده است. سفارش‌های تکمیل‌شدهٔ نسخهٔ قبلی به وضعیت ۵ منتقل می‌شوند و سفارش‌های قبلاً دریافت‌شده به ۴؛ migration تکرار نمی‌شود.

به‌روزرسانی سفارش مشتری هر ۱۵ ثانیه در صفحهٔ سفارش‌ها، فروشنده و پیک هر ۳۰ ثانیه، داشبورد مدیریت هر ۶۰ ثانیه است. دکمهٔ refresh هم وجود دارد.

## پیشنهاد خرید اول

- فقط حساب واردشده و بدون هیچ سفارش قبلی واجد شرایط است.
- فقط **یک واحد از یک نوشیدنی انتخاب‌شده** نصف قیمت می‌شود؛ دو نوشیدنی و دو کیک، فقط یک تخفیف نصف قیمت یک نوشیدنی می‌گیرند.
- قیمت و دسته از دیتابیس خوانده می‌شود؛ مبلغ/discount ارسالی مرورگر قابل اعتماد نیست.
- قفل ردیف کاربر در تراکنش، بررسی سابقه و جدول `first_offer_redemptions` با کلید یکتای کاربر، مانع مصرف هم‌زمان یا دوباره می‌شوند.
- لغو سفارش، امکان استفادهٔ مجدد ایجاد نمی‌کند. نیمِ تومان در قیمت فرد به نفع مبلغ صحیح به پایین گرد می‌شود.
- کد تخفیف فروشگاه قابلیت جداگانهٔ موجود است و مبلغ آن جدا از پیشنهاد یک‌واحدی محاسبه می‌شود.

## احراز هویت پیک و امنیت مدارک

پیک پس از ثبت‌نام می‌تواند وارد شود، اما قبل از تأیید مدارک هیچ دسترسی به سفارش‌ها ندارد. نام و موبایل در ثبت‌نام گرفته می‌شود؛ فرم احراز شامل شماره پلاک، مدل و رنگ وسیله، عکس موتور، عکس پلاک، کارت ملی و گواهینامه موتور است.

وضعیت‌ها: ارسال‌نشده، در انتظار بررسی، تأییدشده، ردشده و نیازمند اصلاح مدارک. مدیر مدارک را می‌بیند و نتیجه را با دلیل ثبت می‌کند. رد/اصلاح اجازهٔ ارسال مجدد می‌دهد؛ درخواست pending یا approved قابل overwrite توسط پیک نیست.

- مدارک decode و به JPEG امن تبدیل و با **AES-256-GCM** در `backend/private-uploads` رمزگذاری می‌شوند؛ این مسیر هیچ static mount عمومی ندارد.
- دسترسی تصویر تنها با نشست معتبر مدیر (انقضای ۸ ساعت) و پاسخ `Cache-Control: no-store` ممکن است.
- فایل‌ها permission محدود دارند و همراه `.env` و uploads از Git خارج‌اند. در محیط واقعی TLS، دسترسی محدود سیستم‌عامل و پشتیبان رمزگذاری‌شده ضروری است.
- حتی تغییر دستی `active=1` بدون `verification_status='approved'` امکان دریافت سفارش نمی‌دهد.
- ورود مدیر، فروشنده و پیک throttle دارد و حوزهٔ نشست‌هایشان جداست.

## داشبورد مدیریت

آمار کل/فعال/غیرفعال کاربران و فروشندگان، وضعیت احراز پیک‌ها، تمام وضعیت‌های سفارش، فروش کل/روزانه/ماهانه، مجموع تخفیف و گزارش عملکرد فروشنده و پیک مستقیماً از دیتابیس محاسبه می‌شود. کاربران و سفارش‌ها جست‌وجوی سمت سرور و صفحه‌بندی دارند؛ محصولات و مدارک و فروشگاه‌ها فیلتر/جست‌وجو و کنترل وضعیت دارند.

تعریف‌ها در رابط مشخص‌اند:

- کاربر فعال: حداقل یک ورود در ۳۰ روز اخیر؛ «غیرفعال» در این آمار به معنی مسدود بودن حساب نیست.
- فروشنده فعال: حساب و فروشگاه هر دو فعال.
- فروش: مجموع مبلغ نهایی سفارش‌های تکمیل‌شده؛ **به معنی تأیید تراکنش بانکی نیست**.
- گزارش روزانه و ماهانه بر مبنای UTC و ماه میلادیِ `created_at` سفارش است.
- تخفیف کل مربوط به سفارش‌های غیرلغوشده است.

## بررسی و تست

```sh
cd backend
npm test
# بررسی syntax
node --check app.js

cd ../frontend
npm run typecheck
npm run build
# در seller-frontend، courier-frontend و admin-frontend هم typecheck و build اجرا شود.
```

تست‌های پیش‌فرض قواعد قیمت، یک‌واحد بودن تخفیف، محدودیت دسته، استفاده مجدد، ماتریس مجوز مراحل، تصویر مربع و رمزگذاری مدارک را بررسی می‌کنند. تست‌های HTTP دسترسی با persistence stub اجرا می‌شوند؛ با تست دیتابیس واقعی یکسان نیستند.

### تست سرتاسری با MySQL واقعی

فقط روی دیتابیس آزمایشی **خالی** با نام منتهی به `_test` اجرا شود. این تست رکورد آزمایشی ایجاد می‌کند و برای دیتابیس واقعی نیست:

```sh
# ابتدا CREATE DATABASE nazmarket_test و تنظیم MYSQL_* برای همین دیتابیس
RUN_MYSQL_TESTS=1 MYSQL_DATABASE=nazmarket_test npm run test:integration
```

در PowerShell متغیرها را با `$env:RUN_MYSQL_TESTS='1'` و `$env:MYSQL_DATABASE='nazmarket_test'` تنظیم کنید. تست شامل migration دوباره، ثبت‌نام فروشنده، تأیید فروشگاه، بانک کالا، محدودیت فروشنده، سفارش هم‌زمان خرید اول، موجودی، اصلاح/رد/تأیید مدارک، رقابت دو پیک، تحویل نهایی، تاریخچه و آمار است. فایل `.github/workflows/verify.yml` همین سناریو را روی سرویس MySQL 8 در CI و Build هر چهار رابط اجرا می‌کند. بدون متغیر فعال‌سازی، تست MySQL **skip** می‌شود، نه موفقیت ظاهری.

## حدود استقرار

درگاه بانکی، SMS و سرویس استعلام رسمی هویت متصل نیستند؛ احراز هویت، بررسی انسانی مدارک است. پرداخت فعلاً در محل و `unpaid` ثبت می‌شود و تسویهٔ آنلاین فعال نیست. استقرار production نیازمند MySQL معتبر، متغیرهای مدیر و کلید امنیتی، رسانه‌های پایدار، HTTPS و بکاپ است. هیچ اطلاعات واقعی یا کلید امنیتی را برای تست در مخزن قرار ندهید.
